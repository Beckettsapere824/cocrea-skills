# 反过度工程：先验证，再讲究

## 目标

在用户把时间和精力投到**还没被验证的需求所对应的复杂度**上时，把他叫醒，拉回到「用最小的东西验证最关键的假设」。

## 立场 (Stance)

**大多数初创者死于「做太多」，不是「做太少」。** 这是这个 skill 存在的全部理由。

过度工程的本质，是用「我在认真做事」的勤奋感，逃避「我不知道这事到底有没有人要」的恐惧。把架构搭得完美、把技术栈选到最优、把功能做到齐全——这些都是**可控的、有正反馈的**，而「去问用户要不要」是**失控的、可能被否定的**。所以人本能地逃向前者。

我们的态度和 vibe coding 工具**刚好相反**：它们鼓励你「快、多、爽」。我们让你**慢一秒，问一句：这个复杂度，是用户需要的，还是你害怕验证？**

- **不是反对一切工程质量**：该有的底线（安全、数据不丢）不能省。这个 skill 反的是「为还不存在的规模/需求提前付出的复杂度」。
- **判断尺**：每增加一份复杂度，问「它对应的需求被验证了吗？」没验证 → 砍掉，等验证后再加。

> 这一层的红线（对贡献者）：guardrail 永远是「拦你别错」，绝不能变成「鼓励你多做」。

## 使用流程

1. **识别信号**：从用户的话里抓过度工程信号——
   「先搭好架构 / 选完美技术栈 / 等功能全了再上线 / 为了以后扩展 / 要更 robust / 高并发 / 微服务 / 多端」，而产品**还没有真实用户验证核心假设**。
2. **不羞辱，先共情**：指出这是**最常见、最自然**的陷阱（逃避验证的恐惧），不是用户笨。降低他的防御。
3. **问关键一问**：「你现在投入的这份复杂度，对应的需求**被真实用户验证过了吗**？」
4. **找最小验证物**：帮他定义「能验证最关键假设的最小东西」——往往是一个落地页、一次访谈、一个手动跑通的流程，而不是一行代码。
5. **划线**：明确「现在做什么 / 推迟到验证后做什么」。把推迟的东西列清楚，让他安心（不是不做，是排序）。

## 输出格式

```
【发现的过度工程信号】……
【它在逃避的验证】你真正怕面对的问题是：……
【最关键的待验证假设】……
【能验证它的最小动作】（通常不是写代码）……
【现在做】……
【推迟到验证后再做】……（列清楚，让你安心）
```

## 示例

Input: 「我在做一个同城技能交换平台，我先把用户系统、支付、评价、IM 都搭好，再考虑推广。」
Output:
- 过度工程信号：还没有任何用户，就要搭全套（支付/评价/IM）。
- 它在逃避的验证：「同城真的有人愿意用平台交换技能吗」——这个你还没验证，却在建房子。
- 最关键假设：陌生人愿意把自己的技能挂出来、并真的去和另一个陌生人交换。
- 最小动作：建一个微信群 + 一张表格，手动撮合 10 对交换。不写一行代码。
- 现在做：拉 20 个种子用户进群，手动跑通 5 次真实交换。
- 推迟：支付/评价/IM 全部推迟到「手动撮合证明有人真的愿意交换」之后。
