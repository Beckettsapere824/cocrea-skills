# MVP 范围裁剪：砍到最小可验证

## 目标

给用户一个**可操作的工具**，把一个大想法砍成「能验证最关键假设的最小可交付物」，并产出一份明确的「做 / 不做」清单。

> 区别于 `anti-over-engineering`（那是「叫醒你别过度」的认知矫正）：本 skill 是**具体怎么砍**的操作工具。两者常配合用——先被叫醒，再用这个动手砍。

## 立场 (Stance)

MVP 不是「功能少的产品」，是「**用最小成本验证一个最关键假设**的实验」。

- **常见误解**：把 MVP 理解成「先做个简陋版的完整产品」。错。MVP 的 M 是「最小」，但 V 是「可行验证」——它必须能**回答一个具体问题**，否则做了也白做。
- **核心纪律**：MVP 围绕**一个**最关键假设来裁，不是围绕「砍掉一半功能」。先问「我最不确定、一旦错了最致命的假设是什么」，再砍到只验证它。
- **边界**：MVP 验证「要不要做」，不验证「能不能赚钱规模化」——那是后面的事，别在 MVP 阶段就要求它回答。

## 使用流程

1. **列全集**：先让用户把想做的功能/范围一股脑列出来（不评判）。
2. **定关键假设**：问「这里面，你最不确定、一旦错了整个想法就崩的假设是什么？」——这是 MVP 要验证的唯一目标。
   - 若用户列了多个假设，逼他排序，只取**最致命的那一个**。
3. **映射**：对全集里每一项，问「它对验证这个关键假设是**必需**的吗？」
   - 必需 → 进 MVP
   - 不必需 → 砍到「以后」
4. **找更轻的替代**：对进了 MVP 的项，再问「有没有更轻的方式达到同样的验证效果？」（手动代替自动、落地页代替功能、人工代替算法）
5. **定成功/失败信号**：MVP 上线前先定义「看到什么算假设成立 / 什么算证伪」——没有这个，MVP 就是白跑。
6. **输出清单**。

## 输出格式

```
【最关键假设】（一旦错了想法就崩的那个）……
【MVP 包含】（仅验证该假设必需的）
  - …… ｜ 更轻的替代方式：……
【砍到以后】
  - ……
【成功信号】看到 …… 说明假设成立
【失败信号】看到 …… 说明假设被证伪，该转向
```

## 示例

Input: 「我要做一个独立游戏发现平台，有推荐算法、社区、评测、开发者主页、内购，第一版做哪些？」
Output:
- 最关键假设：玩家愿意来这里**发现**他们靠 Steam 找不到的独立游戏（而不是又一个商店）。
- MVP 包含：一个每周人工精选 10 款冷门好游戏的列表页（替代方式：推荐算法 → 你手动选；社区 → 先不要）。
- 砍到以后：推荐算法、社区、评测系统、开发者主页、内购，全部推迟。
- 成功信号：连续 4 周，每周有 ≥30% 的访客点进游戏详情/外链。
- 失败信号：访客来了就走，说明「发现」不是真痛点，该转向。
